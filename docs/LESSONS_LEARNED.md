# 지연 원인 회고와 예방 규칙 (Lessons Learned)

작성: 2026-11-23, 대상 기간: P1 / S5b / int8(I1) / PS 연결 비트스트림 / xsim 불일치 조사.
목적: "실제 환경·실제 사용 조건을 먼저 확인하지 않고 일반적인 가정으로 진행해서 생긴 지연"을 분류하고, 다음 설계에서 같은 지연을 막는 규칙을 남긴다.

## 읽는 법 (정직성 표시)
- **시간은 로그 시각과 대화 순서로 어림한 값**이며 정확히 측정한 값이 아니다. 일부는 사용자 대기 시간과 겹친다.
- 각 항목에 **확인 상태**를 둔다: `확인`(로그나 측정으로 확인), `추정`(그럴 가능성이 높지만 증명 못 함), `정정`(앞서 말한 것을 바로잡음).
- 구분: **제 실수**(작업자의 판단 실수) / **환경 제약**(도구·장비의 한계) / **요구 누락**(사용자 조건을 늦게 반영) / **설계 누락**(설계 시 실제 조건 미반영).

## 정정 (먼저 읽을 것)
- **xsim 전체 칩이 DONE에 도달하지 못한 직접 원인은 "SRAM 초기화 누락"이 아니다.** 한때 그렇게 추정했으나, 근거로 든 trace 차이는 저장(store) 응답의 의미 없는 데이터(2상태 0 대 4상태 x)였다. 이를 제외하면 두 시뮬레이터는 9,910 cycle까지 CPU 데이터 포트 이벤트 4,462개가 동일하다(`fpga/xsim/compare_trace.py`).
- 현재까지 확인된 것: xsim에서 VFU가 `XS`(softmax2) 상태에 머물며 `x_req`가 0으로 평가된다. 입력 상태값은 정상이다. 어느 항이 틀린지는 조사 중이다(상태: **미확인**).
- 그래도 테스트벤치가 0 워드를 적재하지 않은 것은 **실제 보드 흐름(전 워드 적재)과 다른 시험 환경**이라서 고쳤다(`fpga/xsim/tb_chip.sv`). 이것이 지연을 만들었다는 증거는 없다.

## 1. 시험 환경이 실제와 달랐던 것
| 사례 | 무슨 일이 있었나 | 지연(어림) | 구분 | 확인 상태 |
|---|---|---|---|---|
| xsim 테스트벤치 SRAM 적재 | 0이 아닌 워드만 적재. 보드 흐름(`pynq/run_chip.py`)은 전 워드를 씀. 4상태 시뮬레이터에서 나머지는 x | 지연 기여는 증명 못 함 | 설계 누락 | 환경 차이 확인, 원인 기여 **추정 철회** |
| xsim 진행 판단 | 로그의 "TB running 2000000"을 cycle 단위로 확인하지 않고 "정상 진행"이라 보고. 이미지는 약 16만 cycle이면 끝나야 했음 | 밤새 약 15시간 | 제 실수 | 확인 |
| 시뮬레이터 하나를 기준으로 삼음 | FPU를 xsim에서만 보고 하드웨어 문제로 이어 갈 뻔함. Verilator·합성 네트리스트·numpy와 교차해 xsim 평가 버그(`FP_ENCODINGS[변수]`)로 확정 | 규명에 수 시간 | 도구 신뢰 가정 | 확인 |
| 낡은 결과 파일과 비교 | xsim FPU 시험 스크립트는 `fpu_out_rtl.hex`가 있으면 RTL 시뮬레이션을 건너뛰는데, 벡터를 3,896개로 늘린 뒤에도 이전 1,402줄 결과 파일을 읽어 "1402/3896 correct"라는 무의미한 결과를 냄. 합성 네트리스트 쪽은 매번 새로 돌아 정상 | 재실행 1회(약 수 분) | 제 실수(스크립트의 캐시 규칙을 확인하지 않음) | 확인 |

## 2. 실행 환경 제약을 늦게 반영한 것
| 사례 | 무슨 일이 있었나 | 지연(어림) | 구분 | 확인 상태 |
|---|---|---|---|---|
| Vivado 프로젝트 실행 흐름 반복 실패 | 멈춤/충돌(EXCEPTION_ACCESS_VIOLATION)이 8회 중 7회 안팎. 같은 흐름을 여러 번 재시도한 뒤 GUI로 전환 | 약 4~5시간 | 환경 제약, 전환이 늦음 | 확인 |
| 동시 작업으로 메모리 부족 | Vivado 합성 중 Verilator 빌드를 병행해 Vivado가 out of memory로 종료 | 합성 1회 재실행(약 30분) | 제 실수 | 확인 |
| 남은 프로세스/폴더 | Vivado만 종료하고 `xsimk.exe`를 남겨 폴더 삭제 실패. 한 번은 작업 폴더 `rtl`(xsim 프로젝트 폴더와 이름이 같음)을 지워 소스 사본 삭제 | 각 10~20분 | 제 실수 | 확인 |
| 감시 스크립트 오탐 | 이전 로그를 읽거나 경로를 잘못 잡아 정체/오류를 오판 | 재시도 2~3회 | 도구 점검 부족 | 확인 |

| 사례 | 무슨 일이 있었나 | 발견 계기 | 비용(어림) | 확인 상태 |
|---|---|---|---|---|
| 외부 읽기 판정을 주소 비교로 구현 | 150 MHz에서 주소→grant 경로 WNS −2.35 ns | 합성 | 합성 3~4회 | 확인 |

| 외부 읽기 플래그가 스케일 적재 단계에서 꺼져 있음 | DDR top에서만 데이터 오류(온칩에서는 안 드러남) | 비트 비교 | 디버그 1회 | 확인 |

## 반복되는 원인
1. 이상적인 조건으로 시험함(보드 흐름과 다른 적재, 지연 없는 메모리, 실제와 다른 클럭 목표).
2. 진행 상태를 단위·종료 조건 확인 없이 "정상"이라 보고함.
3. 요구(클럭 목표, 보드 유무, 합격 기준)를 작업 시작 때 고정하지 않음.
4. 같은 실패를 반복하며 방식을 바꾸지 않음(Vivado 프로젝트 흐름).
5. 무거운 작업을 병렬로 돌림.
6. 시뮬레이터 하나를 신뢰 기준으로 삼음.
7. 타이밍 문제를 구현 후에야 발견함.
8. 캐시된 결과 파일이 현재 입력의 것인지 확인하지 않음(xsim FPU 시험 사례, 11-23).
9. 실험의 세부(구성, 수치, 해석)를 대화에만 남기고 저장소에 남기지 않음(`.scratch`의 원본 출력 70여 개가 git 밖에 있었음, 11-23).

| R6 | **독립 기준 2개 이상**으로 교차한다(Verilator, 합성 네트리스트, numpy 등). 시뮬레이터 하나의 불일치로 하드웨어를 판단하지 않는다 | 불일치 조사 |
| R7 | 합성은 **설계 초안 단계**에서 먼저 한다(타이밍은 구현 뒤에 드러남) | 설계 초기 |
| R8 | 작업 폴더·삭제 대상은 **이름과 경로를 확인한 뒤** 지운다(xsim 프로젝트 폴더와 소스 사본 폴더 이름 충돌 전례) | 정리 작업 |

| R10 | 앞서 한 추정이 새 증거로 약해지면 **즉시 정정해서 보고**한다(이번 SRAM 추정 철회 사례) | 항상 |
| R11 | 결과 파일을 재사용(캐시)하는 스크립트는 입력(벡터, RTL, 설정)이 바뀌었을 때 낡은 결과를 비교하지 않는지 확인한다. 실행 시작 때 결과 파일을 지우거나, 결과 줄 수가 기대값 줄 수와 같은지 검사한다 | 시험 스크립트 작성과 수정 시 |

| R13 | 오래 걸릴 수 있는 실행(시뮬레이션, 합성)은 시작할 때 (1) 시계 시간 상한(`timeout`, 예상의 2~3배), (2) 걸러내지 않는 실시간 출력(`tee`/`--line-buffered`), (3) 상한 설정이 실제로 먹었는지 시작 후 1~3분 안의 확인(진행 cycle 속도), (4) 예상 시간의 1.5배 시점의 진행 확인을 건다. 알림만 기다리지 않는다. WSL에서 Windows 도구를 쓸 때 환경변수는 전달되지 않으므로 파일로 넘긴다 | 장시간 실행 시작 시 (V-G7 첫 실행이 상한 없이 3시간 헛돎, E13) |

## 단계별 체크리스트 (전체)
표기: `R*` = 위 예방 규칙과 대응, `신규` = 이번 회고에서 추가한 세부 항목. 완료한 항목은 `[x]`로 바꿔 쓴다.

### A. 작업 시작 (요구 고정, R3)
- [ ] 클럭 목표를 확인한다(현재 100~125 MHz, 150 MHz는 불필요).
- [ ] 보드 유무와 접근 방법을 확인한다.
- [ ] 합격 기준을 정한다(int8: nll_delta ≤0.01, argmax ≥0.97은 제안 단계이며 사용자 결정 **미정**).
- [ ] 범위를 정한다(15M 모델 파일, 임베딩, KV 위치 등).
- [ ] (신규) 도구 환경을 확인한다: Vivado는 Windows판을 WSL 래퍼로 사용, 메모리 한도, 배치 모드가 안정적인지 GUI가 필요한지.
- [ ] (신규) 결과물 기록 위치(저장소, Notion)와 커밋 시점을 정한다.

### B. 설계 초안 (R7)
- [ ] 합성(OOC)을 설계 초안 단계에서 먼저 돌려 타이밍을 본다.
- [ ] (신규) 주소 비교 같은 긴 조합 경로를 grant 판정에 두지 않는다(WNS −2.35 ns 사례).
- [ ] (신규) 요청 단위를 확인한다(워드 단위가 아니라 라인 단위, 스케일 적재 사례).
- [ ] (신규) 플래그와 모드 신호가 **모든 상태**(ROWS, LOADS)에서 켜지는지 확인한다.
- [ ] (신규) 미해결 요청 상한(CRED)을 지연 × 대역으로 계산해서 정한다.
- [ ] (신규) **온칩 top과 DDR top 두 구성 모두**에서 비트 비교한다.
- [ ] (신규) 함수가 인자가 아닌 모듈 변수를 읽는 경우 `assign`에서 호출하지 않는다(시뮬레이터마다 재평가 여부가 다를 수 있음, 아래 "미완료" 항목 참고).

### C. 테스트벤치와 시험 환경 (R1)
- [ ] 실제 보드 흐름과 같은 조건으로 만든다(전 워드 적재, 지연 있는 메모리, 실제 클럭). 다르면 차이를 문서에 적는다.
- [ ] (신규) 4상태 시뮬레이터에서 초기화되지 않은 메모리가 x가 되는지 확인한다.
- [ ] (신규) xsim을 쓸 때마다 FPU 1,402 벡터(`run_fpu_test.sh`)를 도구 점검으로 먼저 돌린다.
- [ ] (신규) 시험이 실제로 틀림을 잡는지 변이 시험으로 확인한다(전례: 1,019개 불일치).
- [ ] (신규) trace 비교는 의미 없는 값(저장 응답 데이터)을 제외하고 비교한다(`fpga/xsim/compare_trace.py`).

### D. 장시간 실행 중 (R2, R4, R5, R9)
- [ ] R2: 로그 단위(cycle인지 step인지)와 예상 종료 시점을 계산해 비교한다(예상 16만 cycle인데 2.3억이면 이상).
- [ ] R4: 같은 실패가 2회 반복되면 재시도하지 않고 원인을 분리하거나 방식을 바꾼다.
- [ ] R5: Vivado와 대형 시뮬레이션은 직렬로 돌린다.
- [ ] R5: 시작 전과 종료 후에 `tasklist.exe`로 `vivado.exe`, `xsimk.exe`를 확인한다.
- [ ] R9: 감시 스크립트는 로그의 시각과 경로가 새것인지 확인한 뒤 판정한다.

## 미완료·미확인
- xsim에서 VFU가 `XS` 상태에 머무는 현상: 10,037 cycle부터 `x_req`의 모든 항(`st_q==XS`, `src_q<n_q`, `rd_ok`, 크레딧)이 참인데도 `assign x_req`만 0이다(**확인**, 프로브 `XSPROBE`). `rd_ok`를 테스트벤치에서 직접 호출한 값은 1로 바뀐다. 가설: `rd_ok`가 인자가 아닌 모듈 변수(`rd_v_q`, `rd_st_q`, `rd_elem_q`)를 읽어서 xsim의 `assign`이 그 변화에 반응하지 않는다(**미검증**, 작업 복사본에서 `rd_ok`를 인라인해 확인할 예정). 확정되면 `docs/XSIM_VS_VERILATOR.md`에 기록한다(아직 작성 전).
- 합성된 전체 칩 네트리스트 수준의 동작은 FPU 단위 시험(1,402/1,402)만 확인했고 전체 칩은 **미확인**이다. 보드 실행도 하지 못했다.
- 위 시간 값은 어림이며 측정값이 아니다.

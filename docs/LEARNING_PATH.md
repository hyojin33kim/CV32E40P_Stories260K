# RISC-V 개발환경과 칩 수준 지식을 체계적으로 익히는 길 (2026-11-28)

대상: DSP 프로세서(TMS320C2x, 16비트)의 어셈블리 코딩과 사내 어셈블러, 디버거 개발 경험이 있고, 일반적인 RISC-V, 컴파일러, 로더 등 개발환경과 칩 수준 지식이 약한 엔지니어. 이 저장소의 실제 파일을 읽고, 돌리고, 확인하며 한 층씩 올라가는 순서를 정리한다.
표기: **확인함** = 이 저장소에서 직접 확인한 사실, **일반 지식** = 이 프로젝트에서 시험하지 않은 일반론(틀릴 수 있음), **미확인** = 모름.

## 1. 출발점 (사용자가 알려 준 것)
- 이전 경험: TMS320C2x(16비트 DSP). 어셈블리는 **C 소스를 보고 사람이 직접 번역해서** 작성했고, 사내 어셈블러와 디버거를 개발해 본 적이 있다.
- 약한 부분: 일반적인 RISC-V, 컴파일러, 링커, 로더 등 개발환경, 칩 수준(합성, 보드, 디버그) 지식.
- 이 경험의 의미: 컴파일러가 하는 일(C를 어셈블리로 바꾸고 레지스터, 스택, 호출 규칙을 정하는 것)을 사람이 해 본 셈이다. 그래서 **컴파일러가 만든 어셈블리를 읽고 "내가 쓴다면 이렇게 썼을 것"과 비교하는 방식**이 가장 빠르다. 컴파일러 내부를 알 필요는 없다.

## 2. C2x에서 RISC-V(RV32)로: 무엇이 같고 무엇이 다른가 (일반 지식, C2x 세부는 사용자가 바로잡아 주십시오)
| 항목 | TMS320C2x(경험) | 이 칩의 RISC-V(RV32IMFC) | 이 저장소의 실물 |
|---|---|---|---|
| 워드 | 16비트 | 32비트(`sw`, `lw`), 압축 명령은 16비트 | `fw.dis` |
| 주소 | 워드 단위(일반 지식) | 바이트 단위 | `fw.map` |
| 연산 구조 | 누산기 중심, 곱셈 결과 레지스터(일반 지식) | 범용 레지스터 32개, 연산은 레지스터끼리, 메모리는 `lw`/`sw`로만 | `fw.dis` |
| 수 표현 | 정수와 고정소수점(Q 포맷)(일반 지식) | 이 프로젝트는 IEEE-754 fp32를 하드웨어 FPU로 계산. **반올림과 비트 일치가 새 개념** | `docs/XSIM_VS_VERILATOR.md`, FPU 시험 |
| 주소 지정 | 데이터 페이지와 보조 레지스터(일반 지식) | `lw rd, 오프셋(rs1)` 한 가지 | `fw.dis` |
| 호출과 스택 | 작은 하드웨어 스택(일반 지식) | 메모리 안의 소프트웨어 스택(`sp`), 호출 규약(ABI)이 사양으로 정해져 있고 컴파일러가 따름 | 시작 코드가 `sp`를 0x200000으로 설정(확인함) |
| 반복 | 반복 명령(RPT 등)(일반 지식) | 분기 루프. 이 코어에는 하드웨어 루프 확장이 있으나 현재 펌웨어가 쓰는지는 미확인 | `.bss` 지우기 루프(`BOOT_WALKTHROUGH.md`) |
| 입출력 | 별도 I/O 공간 명령(일반 지식) | 메모리 주소에 읽고 쓰기(MMIO) | 가속기 `0x3000_0000`, DONE `0x2000_0000` |
| 코드 작성 | 사람이 C를 보고 번역 | **gcc가 생성**, 사람은 읽고 검증 | `build.sh` |
| 어셈블러와 링커 | 사내 도구 | GNU `as`, `ld`와 링커 스크립트, 결과는 ELF 형식 | `build.sh`, `link.ld`, `fw.elf`(디버그 정보 포함, 확인함) |
| 디버거 | 사내 개발 | RISC-V Debug Spec 0.13.2의 halt, 레지스터 읽기, 단일 스텝, breakpoint(같은 개념) | `dbg/`, `docs/DEBUG_MODULE.md` |

## 3. 단계별 학습 경로 (각 단계: 읽기, 실행, 확인)
1. **ISA와 어셈블리 읽기.** `prof/chip_full_opta_d2/fw.dis`의 `_start` 20줄과 `docs/BOOT_WALKTHROUGH.md`를 대조한다. 레지스터 이름과 역할, `jal`/`jalr`, `lw`/`sw`, 압축 명령(2바이트). 확인: `_start`의 각 줄이 무엇을 하는지 말로 설명할 수 있는가.
2. **툴체인 파이프라인.** `build.sh`가 `.c`에서 `.o`, `.elf`, `.dis`, `.map`을 만드는 과정을 작은 프로그램(`acc/tb_dbgregs/test_dbgregs.c`)으로 한 번 따라간다. 볼 것: 호출 규약(함수 인자가 어느 레지스터로 가는가, 스택 프레임), 섹션(`.text`, `.data`, `.bss`, `.rodata`), 링커 스크립트(`link.ld`)가 주소를 정하는 방법, `readelf`, `nm`, `objdump`. 확인: 직접 쓴 짧은 C 함수를 `-O0`, `-O2`, `-Os`로 컴파일해 어셈블리를 읽고 "내가 C2x에서 손으로 썼다면"과 비교한다.
3. **이미지와 로더.** `image.bin` 구조(SRAM 0~2 MiB, imem은 `0x0100_0000`부터 16 KB)와 AXI 로더 방식을 `docs/BOARD_BRINGUP.md`, `pynq/run_chip.py`에서 읽는다. 사내 로더와 비교한다. 이 칩에는 운영체제 로더가 없고 이미지를 메모리에 직접 써 넣는다(확인함).
4. **메모리 맵과 MMIO.** 펌웨어가 가속기를 부르는 코드(`gen/firmware_gen.c`의 `acc_gemv`)를 읽고 같은 사건을 파형(`docs/figures/waveform_gemv.png`)에서 확인한다.
5. **실행과 관찰, 디버거.** `docs/SIM_HOWTO.md`의 Verilator 실행, 파형, 추적. 그다음 칩 안의 디버거(`docs/DEBUG_MODULE.md`)가 직접 만든 디버거와 어떻게 다른지 비교한다.
6. **칩 수준 흐름.** 합성, 배치배선, 타이밍, 비트스트림, 보드: `docs/P1_REPORT.md`, `docs/VERIFICATION_PLAN.md`, `docs/LESSONS_LEARNED.md`, `docs/figures/rtl_structure.png`, `sw_debug_structure.png`.

## 4. 진행 방식
- 한 번에 한 개념(예: 링커 스크립트). 매번 읽기, 이 PC에서 돌려 보기, 작은 것 하나 바꿔 보기(스택 위치나 `.bss` 범위), 결과 확인.
- 모르는 용어는 C2x와 어셈블러 개발 경험에 연결해 설명하고 짧은 용어표를 쌓는다. 기초 원리는 건너뛴다.
- 외부 자료(일반 지식, 이번에 내용을 확인하지 않음): RISC-V ISA 사양 1권, RISC-V psABI(호출 규약), GNU ld 매뉴얼, RISC-V Debug Spec 0.13.2.

## 5. 위험과 이 권고가 바뀌는 조건
- 범위가 넓어서 깊이를 정하지 않으면 길을 잃기 쉽다. 목표가 "펌웨어를 읽고 고치며 칩을 검증하고 운영"이면 컴파일러 내부는 건너뛰고 2, 3, 5, 6단계에 집중한다. 목표가 "툴체인 직접 개발"이면 2단계를 훨씬 깊게(링커, ABI) 해야 하고 기간이 크게 늘어난다.
- 2장의 C2x 설명은 일반 지식이고 이 프로젝트에서 확인하지 않았다. 사용자의 실제 경험과 다르면 표를 고친다.

## 6. 목표 결정과 실습 (2026-11-28 갱신)
사용자가 정한 목표: (a) 펌웨어 읽기와 수정, 검증과 운영을 포함하고, (b) 툴체인(링커, ABI)은 직접 개발하지는 않지만 개발 과정에 필요한 수준(**LLM → C → RISC-V 어셈블리** 흐름을 읽고 쓸 수 있을 것), (c) 칩 수준(합성, 보드, 디버그)이 최종적으로 얻고자 하는 것.
이에 맞춘 실습 문서는 `docs/LEARNING_LABS.md`(실습 1~9, 실행 명령과 이 PC에서 얻은 결과, 확인 질문과 답)이다. 도구와 예제 프로그램은 `docs/labs/`에 있다(`run_c.py`는 작은 C 프로그램을 컴파일해 칩 시뮬레이터에서 돌리고 결과를 보여 준다).

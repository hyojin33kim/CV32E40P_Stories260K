# 칩 수준 디버깅(ZCU104)에 더 필요한 것 (2026-11-26)

`docs/DEBUG_MODULE.md`는 디버그 모듈(DM)과 JTAG를 칩에 넣고 Verilator에서 확인한 내용이다. 이 문서는 그것으로 **실제 보드에서 디버거(GDB)를 쓰려면 무엇이 더 필요한지**를 정리한다.
상태 표기: **확인함** = 이 저장소에서 직접 확인, **일반 지식** = 이 프로젝트에서 시험하지 않음, **미확인** = 모름.

## 1. 현재 PC에서 확인한 것
- `openocd`와 RISC-V용 `gdb`는 이 PC에 설치되어 있지 않다(확인함: `which`에서 나오지 않음). `riscv64-unknown-elf-` 컴파일러 도구는 있다.
- 펌웨어 ELF(`prof/chip_full_opta_d2/fw.elf`)에는 디버그 섹션이 있다(확인함: 섹션 헤더의 debug 항목 9개). 소스 수준 디버깅의 재료는 있다.

## 2. 필요한 SW 도구
| 도구 | 용도 | 상태 |
|---|---|---|
| OpenOCD(RISC-V 지원판) | JTAG로 DM과 대화하고 GDB 서버를 연다 | 없음, 설치 필요 |
| RISC-V GDB | 소스 줄, 변수, breakpoint | 없음, 설치 필요 |
| JTAG 어댑터 경로 | 보드의 USB-JTAG 또는 외부 어댑터 | 미확인(보드 확인 필요) |
| OpenOCD 설정 파일 | 칩의 IR 길이, 사용자 체인 번호, 메모리 영역 | 없음, 보드에서 맞춰야 함. 시험할 수 없어 만들지 않았다 |

## 3. GDB로 쓸 때의 제약(이 설계에서 나오는 사실)
- **소프트웨어 breakpoint는 쓸 수 없다.** 펌웨어가 있는 imem은 코어가 쓸 수 없는 읽기 전용 경로라 GDB가 명령어를 `ebreak`로 바꿔 넣을 수 없다. **하드웨어 breakpoint는 코어에 1개**(트리거 1개)라서 동시에 1개만 걸 수 있다(확인함: 코어 문서와 시험).
- **디버거로 펌웨어를 올릴 수 없다.** 적재는 AXI 로더(`run_chip.py`)로 한다. 디버거는 올라간 코드를 멈추고 본다.
- **실행 중 메모리 읽기는 안 된다.** SBA(시스템 버스 접근)는 연결하지 않았고 오류로 응답한다. 멈춘 뒤 코어가 직접 읽는 프로그램 버퍼 방식만 쓴다. OpenOCD가 SBA 오류를 받고 프로그램 버퍼로 넘어가는지는 **시험하지 못했다**(OpenOCD가 없음).
- **가속기 내부는 디버거에 보이지 않는다.** 코어가 멈춰도 `gemv_acc`와 `vfu`는 계속 돈다. 그 내부는 성능 카운터와 ILA(`DBG_PROBE`, `docs/BOARD_ILA.md`)로 본다.

## 4. 필요한 RTL, 보드 쪽 작업
1. **BSCANE2 변형의 확인.** Verilator에는 BSCANE2가 없어 시뮬레이션하지 못했다(합성만 함). 보드에서 OpenOCD가 사용자 체인(USER3, USER4)에 접근하는 것이 첫 시험이다. 보드의 JTAG 체인(PS와 PL의 TAP 위치, IR 길이)은 **미확인**이다.
2. **JTAG 경로 결정.** (a) BSCANE2로 보드의 기존 USB-JTAG 사용: 핀이 필요 없으나 OpenOCD 설정이 까다롭고 Vivado와 케이블을 번갈아 써야 한다(일반 지식). (b) 칩 핀에 JTAG을 내고 외부 어댑터 사용: `dmi_jtag_tap.sv`(실제 TAP)를 쓰고 핀 제약이 필요하며 OpenOCD 설정이 단순하다(일반 지식). 어느 쪽이 가능한지는 보드와 어댑터에 달렸다. 이것이 결정 D5와 연결된다.
3. **DM 포함 비트스트림.** 현재 비트스트림(`board_release_125_int8`)에는 DM이 없다. `DM=1 ... DM_BUILD`로 다시 빌드해야 한다(GUI, 사용자 작업). 125 MHz 배치배선은 통과했다(WNS +0.110 ns, E14).
4. **멈춘 채로 시작하는 순서.** 코어를 첫 명령어에서 멈추려면 `CTRL.RUN=1` 전에 `haltreq`를 걸어야 한다(시뮬레이션에서 확인함: `dbg/tb_dm`의 `+EBREAK=1`). 보드에서 `run_chip.py`가 이 순서를 지키는 옵션은 아직 없다.
5. **출력 채널(UART 등).** 펌웨어 `printf`를 볼 방법이 지금은 없다. 디버거와 별개로 가장 쓸모가 큰 도구다. 제안(미구현): 펌웨어가 쓰는 MMIO 한 워드와 AXI로 읽는 레지스터(작고 새 핀이 필요 없음).

## 5. 권고(순서)
1. OpenOCD와 GDB를 이 PC에 설치하고, 시험환경에 `remote_bitbang`(소켓으로 JTAG 핀을 주는 방식)을 붙여 **보드 없이 OpenOCD/GDB 흐름을 먼저 검증**한다. 설정 파일과 GDB 명령(하드웨어 breakpoint 1개, 프로그램 버퍼 메모리 읽기)을 보드 전에 확인할 수 있고, 보드에서는 JTAG 경로만 바뀐다. 작업량은 중간(OpenOCD 설치와 소켓 서버)이다.
2. 보드 확보와 JTAG 경로 결정(D5).
3. UART 대체 출력 레지스터는 디버거와 무관하게 값이 크므로 보드 첫 실행(V-B3) 전에 넣는 것을 고려한다.

이 권고가 뒤집히는 조건: 보드에서 값이 틀렸을 때 시뮬레이션 재현과 덤프 비교, ILA만으로 원인이 충분히 좁혀지면 OpenOCD와 GDB 연동은 필요하지 않을 수 있다(`docs/BOARD_ILA.md`).

## 6. 결정이 필요한 것
- 이 PC에 OpenOCD와 RISC-V GDB를 설치해도 되는지(설치 방식은 네트워크와 권한에 달림).
- JTAG 경로 선호: 보드 USB-JTAG(BSCANE2) 또는 핀과 외부 어댑터.
